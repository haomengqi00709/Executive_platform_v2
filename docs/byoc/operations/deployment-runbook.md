# Deployment runbook — BYOC tier (Azure App Service)

**Audience:** Jason (engineer). The full setup for a new BYOC customer
is in `customer-onboarding.md`; this runbook covers **ongoing**
operations after a customer is live.

## 1. Per-customer project layout

Each customer has their own Azure resources, named with a customer
prefix:

```
Resource group: ceo-platform-<customer>
├── App Service plan: ceo-platform-<customer>-plan
├── App Service: ceo-platform-<customer>
├── Storage Account: ceoplatform<customer>data
│   └── Azure Files share: data
└── Azure Container Registry: ceoplatform<customer>acr
```

Vendor-side:

- GitHub Actions workflow with per-customer secrets.
- Service principal credential issued by customer's Entra ID.

## 2. Required environment variables

The same `_required_env()` calls apply as in SaaS, but values differ
per customer:

| Variable | Purpose | Per-customer value |
|---|---|---|
| `PROD_CLIENT_ID` | Customer's Entra ID app client ID | Provided by customer |
| `PROD_CLIENT_SECRET` | Customer's Entra ID app client secret | Provided by customer (rotate quarterly) |
| `TENANT_ID` | Customer's M365 tenant ID | Provided by customer |
| `SESSION_SECRET` | JWT signing key | Generated by vendor at setup |
| `GEMINI_API_KEY` | Google Gemini API access | Vendor's or customer's, per contract |

### Deployment-specific

| Variable | BYOC value |
|---|---|
| `DATA_DIR` | `/mnt/data` (Azure Files mount point) |
| `REDIRECT_URI` | `https://ceo-platform-<customer>.azurewebsites.net/auth/callback` |
| `FRONTEND_URL` | `https://ceo-platform-<customer>.azurewebsites.net` |
| `APP_URL` | `https://ceo-platform-<customer>.azurewebsites.net` |
| `WEBSITES_PORT` | `8080` (Azure App Service requires this) |

### Optional

| Variable | BYOC value |
|---|---|
| `CLIENT_ID` | Same default as SaaS or customer-specific device flow ID |
| `BETA_ALLOWLIST` | Unset (BYOC is single-customer; no allowlist needed) |

## 3. Build and deploy flow

```
git push origin main
       │
       ▼
GitHub Actions (.github/workflows/azure-deploy.yml)
       │
       ▼
For each configured customer:
  az acr build --registry ceoplatform<customer>acr ...
       │
       ▼
  az webapp config container set ...:<tag>
       │
       ▼
  az webapp restart ...
       │
       ▼
New container live (~5 minutes after push)
```

For 1-3 customers: single workflow with per-customer steps.
For 3+ customers: parameterized workflow with `customer` input.

## 4. Health check

`GET /api/auth/status` should return 200 on the customer's App Service
URL. Configure Azure Monitor availability test per customer.

## 5. Rollback procedure

1. `az acr repository show-tags --name ceoplatform<customer>acr
   --repository ceo-platform` → identify previous good tag.
2. `az webapp config container set --name ceo-platform-<customer>
   --resource-group ceo-platform-<customer> --docker-custom-image-name
   ceoplatform<customer>acr.azurecr.io/ceo-platform:<old-tag>`.
3. `az webapp restart --name ceo-platform-<customer>
   --resource-group ceo-platform-<customer>`.
4. Verify the health check.

## 6. Logs access

- **Live tail**: `az webapp log tail --name ceo-platform-<customer>
  --resource-group ceo-platform-<customer>`.
- **Download**: `az webapp log download` → unzip → grep.
- **Container restart**: Azure portal → App Service → Settings →
  Restart.

## 7. Common operations

### 7.1 Restart the service

```bash
az webapp restart \
  --name ceo-platform-<customer> \
  --resource-group ceo-platform-<customer>
```

### 7.2 Update an env var

```bash
az webapp config appsettings set \
  --name ceo-platform-<customer> \
  --resource-group ceo-platform-<customer> \
  --settings KEY=VALUE
```

Service restarts automatically after env var change.

### 7.3 Rotate `SESSION_SECRET`

1. Generate new value:
   `python -c "import secrets; print(secrets.token_urlsafe(32))"`.
2. Update via 7.2.
3. All users will be logged out and need to re-sign-in.

### 7.4 Rotate `PROD_CLIENT_SECRET` (customer's Entra ID)

1. Customer's Entra ID admin creates a new client secret.
2. Update env var per 7.2.
3. Verify a sign-in.
4. Customer deletes the old secret.

### 7.5 Mount path quirks (Azure Files SMB)

Known issues:

- Mount path **cannot** contain `.` (so `/app/.data` doesn't work; we
  use `/mnt/data`).
- Storage account **must** be `StorageV2` (not `FileStorage`); App
  Service can't mount the latter.
- Mac-built local Docker images **must** specify `--platform
  linux/amd64` or the container won't start on App Service (Mac
  M-series quirk).

These are documented in `docs/CLAUDE.md` "部署：Railway + Azure 双轨"
section.

## 8. Disaster scenarios

| Scenario | Response |
|---|---|
| Customer's Azure region outage | Wait for Azure. Notify customer. No fallback unless customer has multi-region setup. |
| GitHub Actions down | Manual `az acr build` from local. |
| Customer's ACR has a stale `:latest` | Use a specific tag (per-build tag from CI); never rely on `:latest`. |
| Customer accidentally deletes resource group | If customer enabled `CanNotDelete` lock at onboarding, this is blocked. Otherwise: restore from off-RG backup if customer has one; otherwise re-onboard from scratch. |
| Customer revokes service principal access | Cannot deploy until customer re-grants. Vendor cannot self-heal. |
| Lost access to customer's Entra ID admin | Customer must fix; vendor cannot rotate `PROD_CLIENT_SECRET` without it. |
